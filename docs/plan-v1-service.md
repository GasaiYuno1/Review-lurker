# Архитектура, замеры и план ПЕРВОЙ версии (сервис по docs/TZ-v1-service.md) — архив; текущая работа по ТЗ v2: research/REPORT.md

## Сценарий «сначала вопрос» (главный, ТЗ п. 2 и 8)
Файл → маппинг колонок → подготовка один раз (**очистка** правилами + NER, **эмбеддинги**, обзорные темы) → пользователь
пишет произвольный вопрос («нас стали чаще оскорблять за последние 2 месяца?», «сравни, что говорили про приложение
в январе и в июле», «динамика домофона за полгода») → из вопроса извлекаются **период** и **понятие** → обращения
отбираются **по смыслу** (`concept.py`: прототип из предмета запроса, примеров и псевдо-примеров, семантическое расширение
по словарю, пресеты для типовых понятий — негатив, оскорбления и мат, благодарность, отток) → **динамика этого понятия**
(число и доля по дням/неделям/месяцам, всплески и тренды, запрошенные периоды подсвечены) → **сравнение периодов** →
**тематики внутри выборки** (UMAP → HDBSCAN → c-TF-IDF только по отобранным обращениям) → **уточняющий вопрос** по выборке
(ассистент) → калибровка порога по обращениям у границы. С LLM тот же сценарий: критерии из вопроса (несколько понятий),
названия тем, саммари и ответ — через модель.

Обзор всех тем по файлу (без вопроса) — отдельная вкладка: «о чём вообще пишут и что изменилось».

## Модули `src/lurker/`
| модуль | что делает | статус |
|---|---|---|
| `config` | `config.yaml` → dataclass'ы: LLM (endpoint/модель/ключ из env), эмбеддинги, кластеризация, предклассификация, кэш | ✅ |
| `llm` | OpenAI-совместимый `/chat/completions` по HTTP без SDK; кэш ответов; повторы; `FakeLLM` для тестов | ✅ (не проверен на живой модели) |
| `data` | CSV/XLSX (кодировка, разделитель автоматически), маппинг колонок по синонимам и содержимому, даты (ISO и `dd.mm.yyyy`) | ✅ |
| `clean` | Слой 1: структура SMM (саммари / реплики клиента), URL, email, телефоны, счета/договоры/номера заявок, адреса, ФИО регулярками + NER natasha (PER/LOC). Слой 2: LLM few-shot батчами поверх слоя 1 (ПД не уходят во внешний API); сбой батча → результат слоя 1. Кэш sqlite по хэшу текста | ✅ |
| `embed` | `tfidf` (леммы + символьные n-граммы → SVD), `navec` (IDF-взвешенное среднее), `hybrid` (по умолчанию), `st` (sentence-transformers) | ✅ |
| `cluster` | `umap_hdbscan` (по умолчанию), `bertopic` (через библиотеку, те же параметры), `agglomerative`; выбросы → ближайший центроид; слияние тем (`max_topics`/`merge_threshold`); c-TF-IDF ключевые слова; представители; `evaluate` (ARI/NMI/чистота) | ✅ |
| `dynamics` | `timeline` (тема × период, счётчики или доли, фильтры), `compare_periods`, `detect_changes` (всплеск / новая тема / рост / спад; неполные крайние периоды не участвуют в тренде) | ✅ |
| `period` | Период из текста: месяцы, диапазоны, «последние N …», «прошлый месяц», кварталы, даты; относительные — от последней даты в данных. LLM-вариант с тем же результатом | ✅ |
| `preclass` | Критерии (метка: описание, примеры, ключевые слова) из текста или из промпта через LLM; прототипы меток из описания + примеров + «псевдо-примеров» по ключевым словам; отнесение по косинусу с порогом; LLM/гибрид | ✅ |
| `summarize` | Экстрактивные саммари тем (ключевые слова, цитаты, разбивка, динамика), LLM: названия тем, таблица «тема / частота / содержание» + выводы, сравнение периодов; markdown-отчёт | ✅ |
| `concept` | Понятие из промпта: предмет запроса (без периода и служебных слов), пресеты (по леммам и по мату), прототип (эмбеддинг предмета + примеров + псевдо-примеры со всеми словами предмета, ближайшие к прототипу), расширение соседями по navec, оценка = косинус + бонусы за слова предмета (квадратично по доле), пресета и соседей; несколько понятий из LLM-критериев | ✅ |
| `query` | `run_query`: период + понятие → выборка → серия понятия (count/total/share) с находками → сравнение периодов → тематики внутри выборки → текст ответа; `borderline` для калибровки | ✅ |
| `assistant` | Уточняющий вопрос по выборке: релевантные обращения (эмбеддинги + леммы) → счётчики по периодам и темам, цитаты; LLM-ответ (RAG) | ✅ |
| `pipeline` | Подготовка с кэшем (очистка, эмбеддинги, обзорные кластеры), `Analysis`, save/load | ✅ |
| `cli` | `lurker columns/analyze [--prompt]/ask` | ✅ |
| `app.py` | Streamlit «сначала вопрос»: вопрос → метрики, динамика понятия с подсветкой периодов, сравнение, тематики внутри, уточняющий вопрос, калибровка порога; вкладки «Обзор всех тем», «Данные» | ✅ |

## Замеры на тестовых данных (`tools/eval.py`, 3000 строк, 25 тем, скрытая разметка)
- **Очистка**: в очищенных SMM-текстах 0% ссылок, телефонов, email, отчеств, адресов, инициалов; обычные слова не страдают (проверено сравнением словарей до/после на текстах без ПД). Правила: 0.1 мс/текст, с NER: 1.3 мс/текст.
- **Кластеризация** (против истинной темы): hybrid + umap_hdbscan — 42 кластера, NMI 0.80, чистота 0.84, ARI 0.51; tfidf — NMI 0.76; navec — NMI 0.79; агломеративная — заметно хуже (NMI 0.65). Библиотечный BERTopic с теми же UMAP/HDBSCAN даёт ровно тот же результат. Кластеров больше, чем тем: шаблонные фразы генератора дробят тему по формулировкам (это артефакт синтетики); слияние до 25 тем по центроидам роняет чистоту до 0.63, поэтому по умолчанию не укрупняем, в интерфейсе есть ручка.
- **Динамика** по истинным темам находит все заложенные тренды: всплеск домофона в марте (×4.0 по месяцам, ×6.3 по неделям), новую тему с 10 августа, рост угроз ×4.3 и оплаты ×2.7; по кластерам — то же, но всплеск домофона размыт до ×2.6 (кластер шире темы).
- **Предклассификация**: «цифровая / аналоговая услуга» по домофону — точность 1.00 (с псевдо-примерами по ключевым словам; без них 0.995); «оскорбления и угрозы» против всего — точность 1.00 при полноте 0.78 на пороге 0.4 (порог 0.3: полнота 0.88, точность 0.45).
- **Вопрос → выборка по смыслу** (`tools/eval.py --query`, порог 0.5, точность p / полнота r против разметки): «оскорбляли и угрожали физической расправой» p 1.00 / r 0.76 (на пороге 0.4 — 1.00 / 0.80); «благодарности» 0.98 / 0.89; «домофон в приложении» 0.87 / 0.72 (на серии понятия виден всплеск марта: 36 против 15–22); «расторгнуть договор, уходят к конкурентам» 0.95 / 0.75; «не приходит звонок с домофона» 0.75 / 0.78; «мобильное приложение» 0.92 / 0.46 (на пороге 0.4 — 0.89 / 0.84); «нас стали чаще хуесосить?» через пресет мата 0.84 / 0.78 на пороге 0.6; слабее — лексически разнородные понятия без пресета («двойное списание» 1.0 / 0.27, «низкая скорость по вечерам» 0.69 / 0.30): тут нужны примеры (критерии вручную или LLM). Порог — единственная ручка, в интерфейсе с обращениями у границы.
- **Период из промпта**: 20 формулировок в тестах.
- Полный прогон 3000 строк: ~35 с (из них UMAP+HDBSCAN 27 с), повторный — из кэша.

## LLM при бюджете 0
- Для разработки — бесплатные API-тарифы: Gemini (2.5 Flash-Lite, endpoint OpenAI-формата, доступен из окружения разработки), Groq (Llama 3.3 70B), Cerebras, OpenRouter `:free`. Пресеты в `configs/`, лимиты запросов/мин в них выставлены, клиент выдерживает паузы. Данные — только тестовые.
- Для реальных данных — локально: Ollama (`qwen3:8b`, `gemma3:12b`, `t-lite`) на машине с GPU 8–12 ГБ даёт 30–60 токенов/с (полная очистка 3000 комментариев ~15 мин); на CPU в 5–10 раз медленнее. llama.cpp (`tools/local_llm.sh`) — тот же формат API, нужен разовый доступ к huggingface.co. Либо корпоративный endpoint заказчика.
- `lurker llmcheck` — прогон всех шести LLM-шагов на тестовых комментариях со статусом, временем и токенами; `--fake` проверяет саму команду без сети.

## Локальная LLM в окружении разработки: что показал Qwen3-4B (llama.cpp, 4 ядра CPU, `tools/eval_llm.py`)
- **Инфраструктура**: GGUF 2.5 ГБ с huggingface (после открытия `*.hf.co`), сервер `llama_cpp.server` с OpenAI-совместимым API; `tools/local_llm.sh`. Скорость: батч очистки из 10 комментариев 90–180 с, названия 42 тем 8 мин, саммари 15 текстов 2 мин. Для проверки промптов хватает, для прогонов на тысячах строк — Ollama на GPU (см. `docs/run-on-your-pc.md`).
- **Грабли Qwen3**: JSON-грамматика llama.cpp (`response_format`) даёт вырожденный `{}` — в пресетах `json_mode: false`, модель отвечает JSON в ```-ограждении, парсер снимает; режим рассуждений выключается суффиксом ` /no_think` (иначе `<think>` на сотни токенов), `<think>…</think>` на всякий случай вырезается клиентом.
- **Очистка** (20 текстов, половина SMM): правила и правила+LLM дают одинаковые остатки ПД (0) и одинаковое сохранение лексики темы (0.85); LLM меняет 11/20 текстов — убирает ремарки («абон спокоен»), правит опечатки, но иногда портит грамматику («двойная списание»). На синтетике, где структура SMM регулярна, слой LLM не добавляет ничего измеримого; его польза проверяется только на реальном моке.
- **Названия тем**: 42/42 осмысленных («Перерасчёт абонплат», «Домофон в приложении», «Недовольство сотрудником», «Заявка задержана») — главный видимый выигрыш от LLM.
- **Саммари выборки**: таблица «тема / частота / содержание» и выводы получаются связные, для 15 текстов.
- **Период из промпта**: LLM совпал с правилами в 9/20 формулировках, расхождения в пользу правил (сдвиг на день, «с марта по май» → конец 1 мая, «за октябрь» → будущее). Поэтому период всегда берут правила, LLM — только если правила не нашли ничего. Заодно правила научились «за полгода / за год / за N дней» без слова «последние».
- **Критерии из вопроса**: у 4B-модели слабые — примеры вроде «Вы меня обседуют!», лишние метки («Тема_комментария», «Нарушение правил»), ключевые слова в форме существительных. Сами по себе как отбор: лучшая метка «Оскорбления и угрозы» p 1.00 / r 0.33 против p 1.00 / r 0.76 у понятия из промпта. Как *дополнение* понятия из промпта: угрозы без изменений, «домофон в приложении» p 0.87 → 0.40 при r 0.72 → 0.84, мат-промпт p 0.35 → 0.17. Поэтому дополнение критериями выключено по умолчанию (`run_query(llm_criteria_augment=False)`), включать после проверки на сильной модели; попутно ключевые слова стали матчиться по основе («оскорбление» ловит «оскорблял»).
- **Ответ ассистента (RAG)**: связный ответ с цитатами за 37 с.

## Дальше
1. Сильная модель (ключ Gemini/Groq в `LLM_API_KEY`, или Ollama с 8–14B на твоём ПК) → `tools/eval_llm.py` целиком: проверить, начинают ли критерии LLM помогать понятию из промпта (особенно на лексически разнородных «двойное списание», «низкая скорость по вечерам»), и что даёт LLM-очистка на моке заказчика.
2. Мок заказчика: прогнать загрузчик и очистку, поправить регулярки под реальную разметку SMM, перегенерировать тестовые данные под реальную структуру.
3. Эмбеддинги: если у заказчика есть доступ к моделям — `backend: st` с `multilingual-e5-small/base`, сравнить NMI с гибридом.
4. Кластеризация на реальных данных: подобрать `min_cluster_size`, `n_neighbors`, оценить слияние тем на глаз (в синтетике оно вредит, в реальных данных может помогать).
5. Развёртывание: Dockerfile, объём данных 200 МБ (потоковая загрузка, UMAP на 100k+ строк — сэмплирование или `low_memory`).
