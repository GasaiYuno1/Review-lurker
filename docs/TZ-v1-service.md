# ТЗ: сервис семантического анализа комментариев к тикетам

## 1. Контекст

- В подразделениях поддержки используется тикет-система. Сотрудники, общающиеся с абонентами (операторы, SMM и др.), после обращения оставляют тикет: **комментарий в свободной форме + формализованное поле «сервис»** (например «интернет», «мобильное приложение»; сервисы дробятся на подкатегории).
- Пример комментария: «не работает мобильное приложение, жалоба на услугу X, сделали Y, абонент угрожает».
- По формализованным полям метрики уже есть (тысячи, собираются и анализируются без проблем). **Не хватает семантического анализа самих комментариев**: понять, что именно написано, независимо от тематики, даты и других полей.
- Прямая подача комментариев в LLM не работает: нужно анализировать порядка тысячи комментариев за раз, это не помещается в контекст.
- Зачем нужно: динамика негатива; динамика обращений по конкретным услугам; чего хотят абоненты; что хотели в прошлом месяце и изменилось ли это; отзывы/тренды по упоминаниям компании в соцсетях.
- Как возникла задача: исходный вопрос — «стали ли чаще жаловаться на домофон в приложении?». Затем — одна из метрик резко просела, причину по формализованным полям найти не удалось; хотим по комментариям увидеть тренд и понять, что в среднем изменилось в обращениях абонентов. Отсюда решение сделать универсальный инструмент.

## 2. Что важно заказчику

- Архитектура под капотом не важна. Важны ответы на вопросы вида:
  - «как изменилась динамика упоминания услуги X за последние полгода?»
  - «стало ли больше негатива/оскорблений в наш адрес за последние 2 месяца?»
- UX — универсальный: пользователь загружает файл, пишет **произвольный промпт** (например «как часто нас оскорбляли и угрожали физической расправой») и получает:
  1. график динамики,
  2. перечень тематик,
  3. AI-ассистента, которому можно задать уточняющий вопрос по конкретной выборке.

## 3. Входные данные

- Формат: CSV/XLSX, лимит загрузки ~200 МБ.
- **Дата есть всегда** — ключевое поле для динамики.
- Ожидаемые поля (точный набор колонок неизвестен, поэтому нужен маппинг колонок в интерфейсе): текст комментария, дата, сервис/подкатегория, автор/отдел. Помимо динамики по датам пользователю нужна фильтрация по сервису и по конкретному сотруднику, оставившему комментарий.
- **Комментарии сильно различаются по отделам.** У SMM комментарий почти всегда имеет вид: `ссылка → переписка → саммари → персональные данные человека`.
- Реальные данные предоставлены не будут. Заказчик позже сгенерирует мок-файл с похожей структурой, включая «грязные» SMM-комментарии (ссылка/переписка/ПД), чтобы тестировать на мусорных, а не на чистых данных. До появления мока — сгенерировать собственные тестовые данные такой же структуры.

## 4. Ключевое требование: предобработка перед эмбеддингом

- **Сырой текст нельзя подавать в эмбеддинг напрямую.** Иначе модель выделит ссылку как один паттерн, ПД — как другой, саммари — как третий, без осмысленного векторного анализа.
- Обязательный шаг — **очистка текста через LLM в режиме few-shot (3–5 примеров)**: выделить содержательную часть, убрать ссылки, персональные данные, служебную разметку. Возможная реализация: LLM генерирует код/правила очистки по примерам, либо чистит тексты сама.
- **Не путать два разных шага:**
  1. *Предклассификация по теме* — размечает тему (по пожеланиям пользователя, например: «мобильное приложение и звонки в приложении = цифровая услуга; звонки на домофон вне приложения = аналоговая услуга»).
  2. *Очистка входа перед эмбеддингом* — убирает мусор.
  В финальном пайплайне это может быть один LLM-вызов, но задачи разные.

## 5. Роль LLM в пайплайне

LLM обязательна на этапах:

- очистка текста;
- предклассификация по запросу/правилам пользователя;
- саммаризация кластеров — на вход подаются **небольшие, уже выделенные кластеры**, а не весь датасет;
- ассистент по выборке (уточняющие вопросы);
- парсинг периода из текста промпта (см. п. 6).

Модели на этапе разработки (без бюджета):

- Hugging Face Inference API с бесплатными моделями;
- OpenAI API с пробными кредитами ($5–10);
- локальная модель.

**Эндпоинт и имя модели должны быть вынесены в конфиг**: после проверки подхода заказчик заменит их на внутренний корпоративный эндпоинт и доработает код под себя.

## 6. Динамика по времени

Нужны оба способа, один не заменяет другой:

1. **Визуально, без LLM** — график/таблица: ось времени с переключаемой гранулярностью (день/неделя/месяц), количество комментариев по каждой теме/кластеру. Всплеск и спад («в марте всплеск по домофону, в апреле спало») должны быть видны на графике сами по себе.
2. **Через LLM** — период задаётся текстом прямо в промпте («сравни, что говорили про мобильное приложение в январе и в июле», «покажи тренд негатива за последние 3 месяца»), без отдельных фильтров по датам в интерфейсе. LLM парсит период из формулировки и **применяет его как фильтр к данным до** анализа/саммаризации. Этот режим нужен для ответа «что изменилось и почему».

## 7. Уже опробованный MVP и выводы из него

Скриншоты интерфейса: `mvp_screenshot_1.png`, `mvp_screenshot_2.png`. MVP собирался быстро, для оценки трудозатрат, на другом датасете (расшифровки NPS-обзвона) — поэтому в нём есть NPS-метрики, для этой задачи они не нужны.

Пайплайн MVP:

1. Интерфейс на Streamlit.
2. Загрузка CSV/XLSX (лимит 200 МБ).
3. Маппинг колонок (в MVP: текст, готовый LLM-саммари (опционально), город, тип абонента, категория, рекомендация, дата).
4. Пользователь выбирает колонку с комментариями для кластеризации.
5. BERTopic по выбранной колонке; вкладки: обзор, BERTopic (график тем), цитаты, AI.
6. AI-summary: источник — все строки или конкретный кластер; произвольный промпт; результат — таблица «тема / частота упоминаний / содержание» + список выводов «что именно говорят клиенты».
7. LLM-надстройка: пользователь описывает правила отнесения к темам (см. п. 4), LLM генерирует регулярку для предклассификации, результат передаётся в BERTopic.

Что не сработало — не повторять:

- **BERTopic «из коробки»** даёт много мусора и объединяет в один кластер тексты без явной семантической близости; автоназвания тем неинформативны (вида `0_общаться_нравится_поддержкой_вашей`). UMAP/HDBSCAN не настраивались. Считается лучшим вариантом для русскоязычных текстов, поэтому **сначала проверить с нормальной настройкой**, а не принимать качество как данность; если классификация всё равно неточная — выбрать другой инструмент.
- **Регулярки для предклассификации** ловят формальные признаки, а не семантику. Нужен семантический способ предклассификации.
- **Кластеризация на сырых текстах** — см. п. 4, обязательна очистка.

## 8. Ожидаемый результат

- Решение, покрывающее ~90% потребностей в инструменте семантического анализа комментариев.
- Целевая схема: произвольный запрос пользователя (например «нас оскорбляют?») → LLM превращает его в критерии предклассификации → очистка текстов → кластеризация на очищенных данных → динамика по времени + перечень тем + ассистент по выборке.
- Раздел будет дополнен заказчиком вместе с мок-данными.

## 9. Открытые вопросы

- Точный набор колонок входного файла (до мока — маппинг колонок в UI + собственные тестовые данные).
- Какой корпоративный LLM-эндпоинт будет в проде — код должен быть от него независим (конфигурируемый эндпоинт/модель).
- Среда развёртывания не указана.
